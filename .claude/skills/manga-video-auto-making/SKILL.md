# マンガ動画自動作成

## なぜこのスキルが必要か

「あるルールを守らないとどうなるか」を伝える動画は、条文をそのまま読み上げるより、当事者(現場の人)の視点で「やらかした人がどうなったか」「正しくやっている人はどう振る舞っているか」を見せた方が圧倒的に伝わる。このスキルは、銀座のタクシー乗車禁止地区をテーマにした動画を作った際に確立した型を一般化したもの。その型の核心は次の3つ:

1. **事実に裏付けを取ってから書く。** 実在の制度がテーマなら、思い込みや一般論で書かず、公式情報(監督官庁・業界団体など)を検索して裏付けを取る。過去に「AAA評価は個人が持つもの」という誤った前提で書いてしまい、後から「実際は会社が受ける評価だった」と訂正が入ったことがある。当事者本人が知っている前提を軽く聞くだけで防げる間違いなので、着手前に確認する。
2. **「破ったらどうなるか」と「やるべきなのにやらなかったらどうなるか」を両方見せる。** 片方だけだと説教くさくなるか、逆に緩すぎる印象になる。両方の失敗パターンを見せてはじめて「じゃあ正しくはどうするか」が腹落ちする。
3. **文字の台本で終わらせず、実際に動く形にする。** シナリオを書いて終わりだと、依頼者は「これをどう動画にすればいいのか」で止まってしまう。ブラウザで再生できるプロトタイプまで作ることで、画面録画すればそのまま動画ファイルになる状態まで持っていく。

## 全体の流れ

1. 題材とキャラクター設定を確認する
2. (実在の制度・ルールがテーマなら)Web検索で事実確認する
3. 文字シナリオをHTMLで書く
4. 再生できるマンガ動画プレイヤーをHTMLで実装する
5. 品質チェックする
6. Artifactとして公開する
7. (gitリポジトリ内での作業なら)コミット・プッシュする
8. ユーザーに結果と動画ファイル化の方法を報告する

以下、各ステップの詳細。

## 1. 題材とキャラクター設定を確認する

最低限、次が分かっていないと書き始められない。会話に既に情報があればそこから拾い、無ければ聞く:

- **テーマ**: 何のルール・あるあるを扱うか(例:「銀座のタクシー乗車禁止地区」「オフィスの避難通路を塞がない」)。
- **語り手・登場人物**: 誰の視点で語るか。「ベテラン」「新人」「取り締まる側の人」のような対比構造があると失敗談・成功談の両方が作りやすい。
- **評価・目標の紐付け(あれば)**: 「このルールを守ると何につながるか」という動機づけの軸(社内評価、表彰、顧客満足度など)。ここは特に、**その評価が「誰が」「誰に対して」与えるものかを正確に確認する**。個人の人事評価なのか、部署・チーム・会社単位の評価なのか、外部機関からの認定なのかで、登場人物のセリフが変わる。イチバン羽田アプリ(タクシードライバー向け)での実例は `references/taxi-driver-example.md` を参照。他のアプリ・テーマでも、同じ理由で「評価の主体を確認する」という手順自体は流用できる。
- **尺の目安**: 特に指定がなければ3分(180秒)を基準にする。あとで調整しやすいよう、シーンごとの秒数を積み上げて合計が尺に一致するように設計する。

これらが曖昧なまま書き進めると、後から前提の作り直しが発生しやすい。特に「評価の主体」は、本人にとっては当たり前でも外部から見ると誤解しやすい部分なので、一言確認しておくと手戻りがない。

## 2. 事実確認(実在の制度・ルールがテーマの場合は必須)

WebSearchで次を調べ、成果物の末尾に出典として明記する:

- ルールの正式名称・法的根拠(条例、法律、社内規定など)
- 対象範囲・対象時間帯・対象者
- 導入された背景・歴史的経緯(あれば。「なぜこのルールがあるか」を腹落ちさせる材料になる)
- 違反した場合の実際の処分・罰則(個人への処分か、組織への処分か、両方か)
- 一次情報(監督官庁・業界団体の公式サイトなど)を優先し、まとめサイトやブログは裏付けの補強程度に留める

創作寄りのテーマ(実在の法制度に基づかない社内ローカルルールなど)であれば、このステップは軽く済ませるか省略してよい。ただしその場合も「これは実例ではなくフィクションです」という位置づけを成果物のどこかで明確にする。

## 3. 文字シナリオをHTMLで書く

`assets/scenario_template.html` をコピーして編集する。このテンプレートは実際に運用しているダークテーマのカードUIで、次の構成になっている:

- タイトル・概要(尺、形式、語り手、評価テーマなど)
- 登場人物紹介
- 本編シナリオ(シーンごとに: タイムコード、尺(秒)、絵コンテ(演出メモ)、セリフ/ナレーション、テロップ)
- うち1〜2シーンには「解説画像」として、SVGで簡易な図解(規制エリアの地図、比較フローチャートなど)を埋め込む
- 接客・対応フレーズ集(OK例/NG例)
- 実際に起きている事例のまとめ
- 参考情報(出典リンク)

**シーン設計の目安は8〜10シーン、合計尺は依頼された尺(デフォルト180秒)に一致させる。** 各シーンで必ず埋めるべき観点が3つある(依頼に明示されていなくても、この型が効果的なので基本は含める):

1. 正しく対応するとどんな良いことがあるか(動機づけ)
2. ルールに違反する行動をしてしまったらどうなるか
3. 本来対応しなければいけない場面で対応しなかったらどうなるか

3つ目は見落としやすい。「やってはいけないこと」だけでなく「やるべきなのにやらないこと」も失敗パターンとして必ず1シーン以上割く。銀座乗禁地区の例では「路上で乗せてしまう」(1つ目のNG)と「乗り場で正当な理由なく乗車拒否する」(2つ目のNG)の両方を描いた。

CSSのトーン(背景色・カード・バッジ・黄色いテロップ風ラベルなど)はテンプレートのまま使ってよい。ファイル名は保存先のプロジェクトの慣習に合わせ、**日本語の読み方(音読み/訓読み)を必ず確認してからローマ字化する。** 自己判断で読みを決め打ちしない(例:「乗禁」は「じょうきん」であり「のりきん」ではなかった、という実例がある)。

## 4. 再生できるマンガ動画プレイヤーをHTMLで実装する

`assets/manga_video_template.html` をコピーして編集する。このテンプレートは以下を既に実装済みのエンジンなので、**ゼロから書き直さず、`SCENES` 配列とキャラクターの見た目(`PALETTE`)だけをテーマに合わせて差し替える。**

- SVGで簡易マンガ調のキャラクターを描画する`figure()`関数(頭・胴体・表情・ポーズを組み合わせる)
- シーンのムードごとの背景を描く`bgFor()`関数
- 「エリアの地図」を描く`drawMap()`と「2パターン比較のフローチャート」を描く`drawCompare()`、エンディングカードを描く`drawEnd()`(いずれもテンプレート内では`scene`オブジェクトの中のデータを読んで描画するようになっているので、コードを触らず`SCENES`配列側にデータを渡すだけで内容を差し替えられる)
- 吹き出し・テロップ・シーンチップの表示
- Web Speech API (`window.speechSynthesis`, `lang="ja-JP"`)によるセリフの読み上げ。音声合成が使えない環境でも無音のまま進行に支障が出ないようフォールバック済み
- 再生/一時停止/前へ/次へ/音声ON-OFF、進行バー(クリックでシーン頭出し)、現在シーンの絵コンテ・セリフ全文を常に表示するキャプション欄

`SCENES`配列の各要素のスキーマ(テンプレート内のコメントにも同じ説明がある):

```js
{
  id: "S1",              // シーン番号
  tc: "0:00-0:10",        // 表示用タイムコード
  dur: 10,                // このシーンの秒数(合計が尺と一致するように設計する)
  mood: "night",          // 背景のムード。night/room/flash/stand/reflect から選ぶか増やす
  who: "話者名",           // 吹き出しの話者ラベル(ナレーションなら空でもよい)
  telop: "画面下のテロップ文言",
  line: "セリフ・ナレーション本文",
  storyboard: "絵コンテ(演出メモ)。キャプション欄に表示される",
  actors: [               // 画面に出すキャラクター(不要なシーンは省略可)
    {c:"protagonist", expr:"neutral", pose:"stand", x:150, y:180, scale:1}
  ],
  special: "map" | "compare" | "end" | undefined, // 解説画像やエンディングにする場合のみ指定
  map: {...},      // special:"map" のときにdrawMap()が読むデータ(テンプレート参照)
  compare: {...},  // special:"compare" のときにdrawCompare()が読むデータ(テンプレート参照)
  end: {...}       // special:"end" のときにdrawEnd()が読むデータ(テンプレート参照)
}
```

`PALETTE`はキャラクターの役割ごとの色定義。テンプレートには`protagonist`(主人公)・`rookie`(新人役)・`authority`(取り締まる側・注意する側)・`customer`(お客様役)・`rival`(反面教師役)の5役が汎用名で用意してあるので、まずはこの役割名のまま使い、足りなければ増やす。

16:9のステージ(`aspect-ratio:16/9`)が基本だが、縦動画向けにしたい場合はCSSの`aspect-ratio`を`9/16`に変え、キャラクターの配置座標(x, y)を調整すればよい。

## 5. 品質チェック

2つのHTMLファイルについて、保存のたびに構文を機械的に確認する。目視だけで「動くはず」と判断しない(SVGやテンプレート文字列の中の閉じ忘れは目視で見落としやすい):

```bash
python3 -c "import html.parser; html.parser.HTMLParser().feed(open('ファイルパス', encoding='utf-8').read())" && echo "HTML parse OK"

node -e "
const fs = require('fs');
const html = fs.readFileSync('ファイルパス','utf8');
const m = html.match(/<script>([\s\S]*)<\/script>/);
new Function(m[1]);
console.log('JS syntax OK');
"
```

構文チェックは「実行時に壊れていないか」の最低限のふるいでしかない。特に`SCENES`配列を大きく書き換えたときは、`actors`の`x`/`y`座標がステージ(`viewBox="0 0 400 225"`)の範囲に収まっているか、`special`を指定したシーンで対応する`map`/`compare`/`end`のデータを渡し忘れていないかを見直す。

Artifactとして公開する前に、`artifact-design`スキルを一度ロードしておく。この動画プレイヤーは「ホストのテーマに関わらず同じ見た目で良い、単一のダークな映像プレイヤー」という意図的なデザインなので、ダーク/ライト両対応のトークン設計は不要(その判断基準も`artifact-design`スキルの中で説明されている)。一方、文字シナリオ側は通常のドキュメント寄りの成果物なので、同スキルの案内に沿って通常通りダーク/ライト両対応を検討する。

## 6. Artifactとして公開する

2つのHTMLファイルをそれぞれ`Artifact`ツールで公開する。`favicon`・`title`・`description`をテーマに合わせて設定する。

ファイル名を後から変更すると、そのファイルのArtifact URLは変わる(新規発行扱いになる)。変更した場合は新しいURLをユーザーに伝える。

## 7. コミット・プッシュ(gitリポジトリ内で作業している場合のみ)

作業ディレクトリがgitリポジトリで、かつ今回の題材がそのリポジトリの内容(例: イチバン羽田アプリのタクシー関連コンテンツ)に関係する場合は、現在のブランチに対して:

```bash
git add <作成したファイル>
git commit -m "<何を・なぜ追加したかが分かる日本語のコミットメッセージ>"
git push -u origin <現在のブランチ>
```

**題材がそのリポジトリと無関係な場合(動作確認のためのテーマなど)は、無関係なコンテンツをリポジトリに混入させないよう、コミット・プッシュしない。** 成果物はスクラッチディレクトリ等に保存し、Artifact公開のみで報告する。迷ったら、コミットする前にユーザーに一言確認する。

コミットメッセージの末尾に、セッションから指示されている`Co-Authored-By`等の属性行があれば付与する。

## 8. ユーザーへの報告

次を簡潔に伝える:

- 文字シナリオとマンガ動画プレイヤー、それぞれのArtifact URL
- (該当する場合)コミット・プッシュが完了したこと
- **実際の動画ファイル(mp4)にする方法**: このプレイヤーは「ブラウザで再生できるプロトタイプ」であり、自動でmp4を書き出す機能は無い。一番簡単なのは再生しながら画面録画すること(Windows: Xbox Game Bar、Mac: QuickTime Playerの新規画面収録、スマホ: 標準の画面収録機能)。本格的に仕上げたい場合は、各シーンの絵コンテをイラストレーターやAI画像生成に、セリフをVOICEVOX等の音声合成やナレーター収録に渡すとクオリティが上がる、という案内もセットで伝える。
- チャット上にシナリオ本文を貼ってほしいと言われた場合は、HTMLの内容をMarkdown化して提示する(既存のHTMLをそのまま読み上げるのではなく、見出し・箇条書き・表に整形し直す)。
